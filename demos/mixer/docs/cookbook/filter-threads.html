One thread per GPU filter graph

Reviewed 2026-10-06 against mixer-improv at d1dc35fa. Measurements retain their original workload and validation scope; this review does not certify a running deployment.

Current scope. Current GPU filter graphs still use threads: 1. Per-slot scale/filter hooks have been removed; geometry belongs to the compositor or an upstream source transform. Pinned uploads now use an FFmpeg filter graph, also single-threaded. Eligible raw tag-only colour graphs are bypassed.

The mixer runs filter graphs that only stamp metadata or call CUDA filters on one thread. FFmpeg would otherwise start an idle 16-thread slice pool for each of them.

Status: Implemented

Decoder options.threads=1 is a separate optimization: it avoids extra NVDEC surfaces reserved for frame threads. See the decoder baseline and low-DPB demo assets; both savings were already present before the CUarray comparison.

The idea

Each filter_video node builds an FFmpeg filter graph. By default FFmpeg gives every graph a slice-thread pool with one thread per CPU: 16 on the T4 test host. A graph of setparams or scale_cuda never uses that pool. The GPU does the pixel work, and the node's own thread calls the filters.

At a glance

  • What

    A new node parameter threads on filter_video and filter_audio. It sets the graph's nb_threads before parsing. The default, 0, keeps FFmpeg's choice, so other apps are unchanged. A negative count is rejected when the node is created: the node assigns nb_threads directly, so FFmpeg's own range check for its threads option never runs.

    The mixer's CUDA backend passes threads: 1 for its GPU and metadata graphs: colour where needed, transition, aux SDR conversion, rendition conversion (the graph named scale_<id>; a rendition of another size is scaled before it by cuda_transform, which has no filter graph), and the raw-file setpts/hwupload pair (the pinned raw chain also uses an FFmpeg upload filter; the browser settb/setparams graph has since been dropped, and the browser chain has none either).

  • WhyFFmpeg starts one slice thread per CPU for every graph (16 on the T4 test host), even when the graph does no CPU pixel work. Measured live: 1,088 threads in mixer_color_sdr, 448 in mixer_color_bro, 3,689 in the mixer process, mostly idle (12 % CPU).
  • Latency

    Program: none, 0 frames.

    Command-to-screen: none, 0 ms.

    These graphs never hand work to the slice pool, so the same thread runs the same filters as before. Expected from the code path, not measured.

  • Side effectsNone expected. To confirm on the test host, compare CPU per thread group and the thread count before and after. User filter graphs and the CPU wipe format conversion keep FFmpeg's default pool.
  • Cost1 node parameter and a few lines of code. 0 nodes, 0 queues, 0 VRAM. Threads: about 1,600 idle threads gone.
  • RiskA CPU filter placed in one of these graphs would run on one thread and could get slower. Per-slot filter hooks have been removed; upstream source filters must respect their processing budget. Apps that don't set threads see no change.
  • Switch it offDrop the threads parameter. For the whole mixer, set CudaMixerBackend.graph_threads = 0, which is FFmpeg's default.

Where in the code

  • src/nodes/filters.cpp: reads threads (default 0); source reject a negative count; source set nb_threads before parsing, because FFmpeg starts the pool when it allocates the first filter; source is the member.
  • pyplumber/mixer/backends/cuda.py: graph_threads = 1; source the transition graph. Contract: pyplumber/mixer/backend.py.
  • pyplumber/mixer/graph.py: colour graphs; source source colour routing; source source contracts.
  • pyplumber/mixer/aux.py: aux SDR conversion.
  • pyplumber/mixer/application.py: rendition conversion. The source normalisation of a large catalogue was a filter graph here too; it is a cuda_transform now (source) and has no graph.
  • pyplumber/mixer/dmabuf_inputs.py: the browser settb/setparams graph has since been dropped; the browser chain has no filter graph of its own.
  • pyplumber/mixer/inputs.py: raw-file setpts and hwupload.
  • Kept at FFmpeg's default: the wipe format conversion, pyplumber/mixer/graph.py.
  • Tests: tests/mixer/test_backend.py, tests/mixer/test_graph.py.
  • Docs: NODES.md · filter_video, filter_audio (the threads parameter, an int >= 0).
