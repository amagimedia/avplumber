One decoded frame in flight per NVDEC source

Reviewed 2026-10-06 against mixer-improv at d1dc35fa. Measurements retain their original workload and validation scope; this review does not certify a running deployment.

Current scope. This queue-shrinking proposal remains unselected. CUarray decode retains three decoded queue slots. Removing a downstream input FPS node is a separate queue reduction and does not shrink that decoder queue.

This earlier proposal was not selected. The implemented NVDEC CUarray path keeps the decoded queue at three frames and AUX latency at 80 ms, saving 4.88 GiB in the matched 192-input / 20-output comparison.

Status: Not selected, not in code

The original linear-CUDA analysis below is retained as background. Its estimated queue savings were not measured or shipped and do not describe the new fixed array pools.

  • 3 → 1decoded frames parked per NVDEC source, only at ≤30 fps
  • ≈255 MBVRAM it would free across 40 sources at 1080p, up to ~320 MB (estimate, not measured)

The idea

At a glance

  • What

    Plan each NVDEC source's decoded edge, input_<n>_decoded, at capacity 1 when the show runs at 30 fps or below. At 50/60 fps, and on every other edge, the instance default of 3 stays.

  • Why

    That edge is always full, so its size is pure VRAM held in the decoder's frame pool. Two fewer 1080p frames of 3.19 MiB × 40 sources ≈ 255 MB, up to ~320 MB (estimate).

  • Latency

    None: 0 frames on program and on command-to-screen. realtime releases file frames at their timestamps, however far the decoder runs ahead. A live input's decoded queue is normally empty anyway.

  • Side effects

    Less slack before a decode hiccup forces a repeated frame: 1 frame (33–40 ms) instead of 3. Loop wraps are the likely trigger: 2 s test clips wrap about 20 times a second across 40 sources.

  • Cost

    VRAM: about 255 MB less across 40 sources (estimate). No new nodes, queues or threads. No extra GPU or CPU work. A rate check in mixer.py and one planCapacity call per NVDEC source on both build paths.

  • Risk

    A rise in repeated frames on file sources. The edge queue is bounded and never allocates (try_enqueue), so capacity 1 is a hard cap on parked frames.

  • Switch it off

    Nothing to switch today: the code has no such setting, and every decoded edge keeps the instance default of 3. If it is built, it should be off by default. Capacity 2 would not halve the change: it behaves like 3.

Original acceptance criteria

The proposal required a separate repeat-rate comparison at capacities 3 and 1, using force_fps duplicated counters and compositor repeats per hour. That validation was not performed. The current configuration retains capacity 3.
