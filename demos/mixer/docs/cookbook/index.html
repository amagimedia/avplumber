Mixer optimization cookbook

Implementation links are pinned to develop at c20464a5 (2026-10-09). The mixer has changed since; this page was checked against develop at 8fa15c92 on 2026-10-13. Measurements retain their original workload and scope. Watch the current 192-input L4 demo.

Every capacity-demo scene source is a unique, independent input of at least 1080p25, processed every frame, so no optimization may take a shortcut that real inputs would not allow. Each change is explained with what it does, why, what it costs, its risk and how to switch it off before it ships.

Current demonstration. The 10-second recording shows the real two-viewer interface: Program/Preview, dirty Program, four keys and direct cuts on the 192-input L4 show. It is separate from the capacity measurements below.

Top 10 optimizations to preserve

Ranked for this large mixer workload by measured benefit, graph simplification and operational value. All ten are on develop; this is not a list of ten unclaimed future speedups.

  1. NVDEC CUarray storage — 4.88 GiB saved in the matched historical 192-input / 20-output comparison.
  2. Return browser frames one per new frame — At 192 sources and 1080p30 on the L4: Program deadlines missed in ten minutes fell from 28 / 21 to 0 / 0, and new browser buffer imports from about 10 a second to none.
  3. Read raw frames straight into page-locked memory — 192 sources at 1080p30: the mixer fell from 679 to 510 % of a core and lost 141 threads; the 47 upload threads are gone.
  4. Wait for sources with epoll — The busiest thread, Program compositor A, fell from 51.8 to 34.7 % of a core; the 20 AUX compositors from 80.8 to 45.4 %.
  5. Pacing loops: no spin, four shards — Each loop fell from 26–30 % to about 8 % of a core at 30 fps once realtime stopped spinning on a time base finer than the clock; four shards bound per-loop timer work.
  6. Colour tags at the fan-out — A source whose colour stage only tagged has no colour filter and no thread for one: 141 threads fewer on the 192-source SDR show.
  7. Remove input force_fps — 152 nodes and queues saved; exact fractional cadence GPU-tested.
  8. Single-thread GPU filter graphs — Avoids an idle FFmpeg slice pool per graph; historical savings around 1,600 threads.
  9. Event-driven browser handoff — Historical browser CPU fell from 4.71 to 3.47 cores; polling wakeups fell sharply.
  10. Subscribe only visible AUX tiles — Avoids off-page AUX drawing and frame retention; source decoding continues.

Implemented recipes and measurements

  • Opt-in, measured on L4NVDEC arrays without a staging copyAt 192 inputs and 20 outputs: 20.65 → 15.77 GiB, saving 4.88 GiB (23.7%). Fixed pools and direct array sampling supported earlier 28-output probes; current SDR25 admission is 26 outputs while decoded queues stay at three frames.
  • Live, on by defaultBrowser frames go back one per new frameFrames returned in bunches made Chromium's pool destroy and allocate buffers; each new buffer was a CUDA import and a release that held the CUDA library's lock against every other GPU call. One return per arriving frame, from a return queue of three in a frame queue of nine: at 192 sources and 1080p30, Program deadlines missed in ten minutes 28 / 21 → 0 / 0, AUX 97 → 0, imports about 10 a second → none. The 30 fps limit rose from 170 to 192 sources.
  • LiveRaw frames read straight into the memory the GPU readsA raw NV12 source copied each 3.1 MB frame twice on the CPU before the GPU saw it. One node now reads the file straight into page-locked memory and uploads from there: one thread per raw source where there were four. On the 192-source show the 47 upload threads (132 % of a core) are gone and the mixer fell from 679 to 510 % of a core, 1,327 to 1,186 threads, with no missed deadline in the first hour.
  • LiveThe compositor's wait costs the frames that arrivedThe busiest thread of the 192-source show waited for its sources with poll(): 193 descriptors on each of about 2,200 wakes a second. With epoll, Program compositor A fell from 51.8 to 34.7 % of a core (kernel time 17.4 → 3.0) and the 20 AUX compositors from 80.8 to 45.4 %, with no change in when the thread wakes. On one tree with and without the commit: 43 → 32 %. A second commit drops two unused passes over the inputs: AUX compositors 44 → 32 %. Projected for 1080p50: 84 → 51 %.
  • LiveColour tags at the fan-outA source whose declared colour already matches the canvas needs its frames tagged and nothing else, and had a filter node and a thread for that. The fan-out every source has anyway now stamps the tags: browser sources, and decoded sources that declare their storage format, have no colour filter. On the 192-source SDR show at 1080p30 that removed 141 colour threads; the mixer went from 1,472 to 1,327 threads.
  • LiveEvent-loop shardingSource pacing timers are spread over four event-loop threads, which bounds the modeled quadratic timer work per loop. Most of what a loop cost at 30 fps was realtime spinning on a time base finer than the clock: with that fixed, each loop fell from 26–30 % to about 8 % of a core.
  • Profile-specific limitsSource limits by mode and frame rateL4 CUarray SDR at 25 and 30 fps: 192 inputs including four keys and 256 scenes, with an output ceiling of 26 at both rates; the 30 fps show ran with 24. Current admission limits and historical T4 measurements are separated by GPU, format and frame rate.
  • LiveOne main CUDA stream, one per monitorThe program runs on one CUDA stream; each aux monitor gets its own non-blocking stream, isolating stream ordering while GPU resources remain shared.
  • LiveMultiviewer: 192 sources, 12 at a timeThe recorded L4 show has 16 pages of 12 equal tiles. Only the 12 on screen send frames, so off-page sources add no AUX draw or retained AUX frame; upstream decoding remains active.
  • Implemented; historical test deploymentBrowser frame hand-offThe browser's frame socket thread waits in poll() instead of waking every millisecond, and failed pages reload without dropping the mixer's connection, holding their last frame while they do. The new browser image used 1.2 fewer cores at 110 sources; the hold is not measured yet.
  • Implemented; historical test deploymentBrowser CPU is per painted frameChromium costs ~3.5 ms CPU per delivered frame per window, whatever the page. A test page that rests two thirds of the time and Electron 44: Electron 5.90 → 2.83 cores, host idle 28 → 50 % at 68 inputs, 60 fps. A later audit splits the cost: 1.5–1.9 ms per painted frame, and 1.1–1.4 cores for ticks that come whether a window paints or not.
  • Implemented; historical test deploymentKeeping Vulkan out of the GPU processRecreating all browser windows crashed Chromium's GPU process and killed workers. WebGPU on OpenGL ES and no crash limit: 5 restarts, 0 crashes.
  • Opt-in, measured on L4Browser frame ticks staggered at 60 fpsEvery 60 fps browser window ticked at the same instant: a 2 ms spike of about 57 runnable threads per frame on 16 vCPUs, and a one-minute load average floating between 9 and 23 at 53 % CPU. With each worker at its own phase: peak 57 → 22.9, threads waiting for a CPU 4.55 → 1.30, 0 missed deadlines before and after.
  • Measurement methodMeasuring CPU pressure at 60 HzLoad average 25 on 16 vCPU at 69 % busy: ready-thread sampling, PSI and schedstat show one ~8 ms burst per 16.7 ms frame from ~6 threads per source. Later traced to the browser windows' frame clock, where it is a 2 ms spike.
  • LiveReal 1080p inputs, no shortcutsThe ground rule: every capacity-demo source is its own input of at least 1080p25, with its own media, processed on every frame.
  • LivePGM delay instead of a longer aux deadlineThe Program preview matches only its PGM pad one frame back, so its 100 source pads keep the normal 80 ms deadline.
  • LiveDSK fades in one passA key fades by weighting its alpha in the existing keyer pass: no second compositor, and frames without a fade run the old kernels.
  • LivePrewarmed DSK keysKeys stay subscribed while off, so a key cut or fade-in starts on the next program frame instead of 1–2 frames later.
  • LiveOne thread per GPU filter graphGPU and metadata-only filter graphs run on one thread instead of an idle 16-thread FFmpeg slice pool each.
  • LiveOne reference frame for monitor encodersAUX encoders keep one NVENC reference frame, because without B-frames each frame is predicted from the previous one.
  • LiveUnused GPU contextsRemoves an OpenGL context in every browser importer and a process-wide CUDA context. Both held memory and drew nothing.
  • Implemented; cadence GPU-testedNative input cadenceRetains realtime, removes 152 input FPS nodes in the captured show, and preserves fractional source periods with a 1/120000 time base.
  • LiveLooped clips keep counting across the wrapA looped file's next pass is shifted by the length of the one before, so timestamps keep rising and a wrap no longer costs the source a frame: about 0.9 drops/s per source with 2 s clips before.

Integration and validation scope

  • Built, Python tests pass; dedicated wipe GPU qualification pendingA wipe clip is cached whole or the start failsA stalled GPU upload on a fresh container was taken for the end of a clip: one wipe was stored with 2 frames instead of 120, the next with 129. A load now ends on the end-of-stream marker, its frame count is checked, and compiled CUDA kernels are kept on the media volume.
  • Implemented; primitive and mixer integration GPU smokes passcuda_transform, the shared geometry nodeOne CUDA frame in, one frame per output canvas, drawn by the compositors' own module; an output that would only repeat the input gets the input frame itself. Source transforms, catalogue normalization and resized renditions use it. GPU integration smokes pass; no full-show throughput comparison is claimed.
