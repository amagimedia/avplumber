Mixer optimization cookbook

Every source is a unique, independent input of at least 1080p25, processed every frame, so no optimization may take a shortcut that real inputs would not allow. Each change is explained with what it does, why, what it costs, its risk and how to switch it off before it ships.

Live

  • LiveOne main CUDA stream, one per monitorThe program runs on one CUDA stream; each aux monitor gets its own non-blocking stream, so a slow monitor cannot stall the program.
  • LiveMultiviewer: 100 sources, 12 at a timePages of 12 equal tiles. Only the 12 on screen send frames, so off-page sources cost no GPU work and no VRAM.
  • Implemented, deployed on the test hostBrowser frame hand-offThe browser's frame socket thread waits in poll() instead of waking every millisecond, and failed pages reload without dropping the mixer's connection, holding their last frame while they do. The new browser image used 1.2 fewer cores at 110 sources; the hold is not measured yet.
  • Implemented, measured on the live demoBrowser paints numbered on the canvas gridEach browser paint takes the previous tick plus one instead of its arrival rounded to the nearest tick. On a 64-source 30 fps show, browser repeats and discards fell from 1,234 and 1,237 to 7 and 25. DSK keys are drawn by timestamp.
  • Implemented, deployed on the test hostBrowser CPU is per painted frameChromium costs ~3.5 ms CPU per delivered frame per window, whatever the page. A test page that rests two thirds of the time and Electron 44: Electron 5.90 → 2.83 cores, host idle 28 → 50 % at 68 inputs, 60 fps.
  • Implemented, deployed on the test hostKeeping Vulkan out of the GPU processRecreating all browser windows crashed Chromium's GPU process and killed workers. WebGPU on OpenGL ES and no crash limit: 5 restarts, 0 crashes.
  • Measurement methodMeasuring CPU pressure at 60 HzLoad average 25 on 16 vCPU at 69 % busy: ready-thread sampling, PSI and schedstat show one ~8 ms burst per 16.7 ms frame from ~6 threads per source.

Being measured

  • Experimental, measured at 25 and 30 fpsRate-aware capacity budgetsNVDEC gets 1100 decoded frames/s instead of a fixed stream count (40/36/22/18 at 25/30/50/60 fps); a fifth browser worker and pinned raw uploads fill 110 inputs at 25 and 30 fps. NVDEC measured 81–82 % at 25 fps and 88.5 % at 30.
  • Implemented, measuringCentred force_fps phaseSource pacers shift a source's timestamps so its first frame lands on an output tick, so timing jitter no longer turns into a repeated frame plus a dropped one. Before it, one raw source at 30 fps repeated and dropped about 10 frames/s each.
  • Setup default, passes the 60 fps A/BRaw uploads and the CUDA driver lockRaw NV12 and P010 frames go through a pinned buffer on the source’s own stream instead of a synchronous copy that holds a lock the whole mixer shares. The setup’s 110-input shows use it for 30 raw sources at 25 fps and 34 at 30. At 68 inputs and 60 fps, hwupload missed 69 % of program deadlines; pinned missed 0.

Implemented

  • ImplementedLooped clips keep counting across the wrapA looped file's next pass is shifted by the length of the one before, so timestamps keep rising and a wrap no longer costs the source a frame: about 0.9 drops/s per source with 2 s clips before.

Implemented, not deployed

  • Implemented, not deployedReal 1080p inputs, no shortcutsThe ground rule: every capacity-demo source is its own input of at least 1080p25, with its own media, processed on every frame.
  • Implemented, not deployedPGM delay instead of a longer aux deadlineThe Program preview matches only its PGM pad one frame back, so its 100 source pads keep the normal 80 ms deadline.
  • Implemented, not deployedDSK fades in one passA key fades by weighting its alpha in the existing keyer pass: no second compositor, and frames without a fade run the old kernels.
  • Implemented, not deployedPrewarmed DSK keysKeys stay subscribed while off, so a key cut or fade-in starts on the next program frame instead of 1–2 frames later.
  • Implemented, not deployedOne thread per GPU filter graphGPU and metadata-only filter graphs run on one thread instead of an idle 16-thread FFmpeg slice pool each.
  • Implemented, not deployedOne reference frame for monitor encodersThe two monitor encoders keep one NVENC reference frame, because without B-frames each frame is predicted from the previous one.
  • Implemented, not deployedEvent-loop shardingSource pacing timers spread over four event-loop threads, so wake-up cost stops growing with the square of the source count.
  • Implemented, not deployedUnused GPU contextsRemoves an OpenGL context in every browser importer and a process-wide CUDA context. Both held memory and drew nothing.

Proposed, not in code

  • Proposed, not in codeOne decoded frame in flight per NVDEC sourceAt 30 fps and below, each NVDEC source could park one decoded frame instead of three: about 255 MB of VRAM across 40 sources, no added latency.
