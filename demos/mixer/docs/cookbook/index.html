Mixer optimization cookbook

Ten current recipes for lowering CPU and GPU overhead while preserving real input cadence, colour and visible delivery.

Reviewed 15 October 2026 against e72ff8b4. These pages describe that code and named workload settings; they do not assert what every deployment runs.

The order prioritizes the current browser-heavy L4 investigation and the recent CPU work. It is not a universal ranking by percentage saved. Implementation descriptions are checked against the revision above; measurements retain their original workload and date.

Top ten to preserve

  1. 1. CUDA work queues: 32 compute / 8 copyReduce unintended serialization between independent streams; separate this setting from buffer counts.
  2. 2. Direct input routing and optional metadataRemove demux hand-offs, unused timestamp strings and redundant per-input resampling.
  3. 3. Shared pacing loops and coalesced signalsRemove per-source fan-out threads, redundant event writes and self wake-ups.
  4. 4. Ready-input handling and bounded pollingInspect useful queues and keep superseded frames out of the hot path.
  5. 5. GPU-native decode with bounded lookaheadSkip software HEVC table clears, avoid staging copies and retain enough decoder surfaces.
  6. 6. Pinned direct and resident raw inputsRemove CPU copies and upload threads; account explicitly for pinned RAM.
  7. 7. Fixed browser pools and early lease releaseOptional exporter: prewarm nine allocations, copy once into AVP ownership and avoid on-air import churn.
  8. 8. Colour tags at the source fan-outAvoid tag-only filters and their threads while preserving real conversions.
  9. 9. Cropped keys and transparent-pixel fast pathsKeep full detail where the overlay exists and avoid work on invisible pixels.
  10. 10. On-air capture identity and lean statusVerify visible source delivery after output pacing; exclude setup and intentional static holds.

Start with the right defaults

Layer What the reviewed configuration selects
L4 deployment 32 CUDA compute queues, eight copy queues; browser frame staggering enabled
L4 source profile Resident raw files; event-loop fan-out; Program/AUX input polling 8 ms; decoded lookahead one; raw pool ten
L4 CUarray decode HEVC, CUarray storage, twelve extra decode surfaces
Browser installation Stock Chromium/Electron plus shim by default; optional exporter needs a compatible patched build
Moving-browser experiment Fixed prewarmed pool nine, AVP copy on import, 4 × 10 windows at 50 fps; 3 × 10 at 60 fps with AUX p1

Generic library defaults differ. Each recipe names which settings belong to a profile, deployment override or optional build. Neither a browser ring nor CUDA queue count sets the compositor deadline.

What was actually demonstrated

Read the current workload and limits before choosing a count: 40 moving windows at 25/30/50 fps and 30 at 60 fps were short checks with 32-layer transitions, with isolated repeats in some runs. They are not a claim of flawless sustained output or 40 windows at 60 fps.

The recorded mixer UI is a separate demonstration. Older CPU, memory and capacity experiments remain in historical evidence; obsolete browser, stream and branch-state advice has been removed from this recommendation list.
