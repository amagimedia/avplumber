Mixer optimization cookbook

Reviewed 2026-10-06 against mixer-improv at d1dc35fa. Measurements retain their original workload and validation scope; this review does not certify a running deployment.

Every capacity-demo source is a unique, independent input of at least 1080p25, processed every frame, so no optimization may take a shortcut that real inputs would not allow. Each change is explained with what it does, why, what it costs, its risk and how to switch it off before it ships.

Top 10 optimizations to preserve

Ranked for this large mixer workload by measured benefit, graph simplification and operational value. Most are already implemented; this is not a list of ten unclaimed future speedups.

  1. NVDEC CUarray storage — 4.88 GiB saved in the matched historical 192-input / 20-output comparison.
  2. Pinned raw uploads — Historical T4 deadline misses fell from 69% to zero; replacement FFmpeg filters have data/cadence smoke coverage.
  3. Remove input force_fps — 152 nodes and queues saved; exact fractional cadence GPU-tested.
  4. Event-driven browser handoff — Historical browser CPU fell from 4.71 to 3.47 cores; polling wakeups fell sharply.
  5. Single-thread GPU filter graphs — Avoids an idle FFmpeg slice pool per graph; historical savings around 1,600 threads.
  6. Grid-based browser timestamps — Historical repeats/discards fell from 1,234/1,237 to 7/25.
  7. Stagger 60 fps browser ticks — Opt-in; historical runnable-thread peak fell from about 57 to 22.9.
  8. Shard pacing event loops — Four shards bound per-loop timer work; the fourfold total N²-term reduction is modeled, not measured throughput.
  9. Subscribe only visible AUX tiles — Avoids off-page AUX drawing and frame retention; source decoding continues.
  10. Bypass redundant raw colour tags — 32 further nodes and queues for the captured matched-SDR show; latest change has no new capacity benchmark.

Implemented recipes and measurements

  • Opt-in, measured on L4NVDEC arrays without a staging copyAt 192 inputs and 20 outputs: 20.65 → 15.77 GiB, saving 4.88 GiB (23.7%). Fixed pools and direct array sampling supported earlier 28-output probes; current SDR25 admission is 26 outputs while decoded queues stay at three frames.
  • Live: setup defaultSource limits by mode and frame rateOne table for SDR, HLG 4:2:0 and HLG 4:2:2 at 25, 30, 50 and 60 fps: 110/90/81 at 30 fps, 75/61/55 at 60, with per-type caps, the Balanced mix at each limit and what runs out first.
  • LiveOne main CUDA stream, one per monitorThe program runs on one CUDA stream; each aux monitor gets its own non-blocking stream, isolating stream ordering while GPU resources remain shared.
  • LiveMultiviewer: 100 sources, 12 at a timePages of 12 equal tiles. Only the 12 on screen send frames, so off-page sources add no AUX draw or retained AUX frame; upstream decoding remains active.
  • Implemented, deployed on the test hostBrowser frame hand-offThe browser's frame socket thread waits in poll() instead of waking every millisecond, and failed pages reload without dropping the mixer's connection, holding their last frame while they do. The new browser image used 1.2 fewer cores at 110 sources; the hold is not measured yet.
  • Implemented, measured on the live demoBrowser paints numbered on the canvas gridEach browser paint takes the previous tick plus one instead of its arrival rounded to the nearest tick. On a 64-source 30 fps show, browser repeats and discards fell from 1,234 and 1,237 to 7 and 25. DSK keys are drawn by timestamp.
  • Implemented, deployed on the test hostBrowser CPU is per painted frameChromium costs ~3.5 ms CPU per delivered frame per window, whatever the page. A test page that rests two thirds of the time and Electron 44: Electron 5.90 → 2.83 cores, host idle 28 → 50 % at 68 inputs, 60 fps. A later audit splits the cost: 1.5–1.9 ms per painted frame, and 1.1–1.4 cores for ticks that come whether a window paints or not.
  • Implemented, deployed on the test hostKeeping Vulkan out of the GPU processRecreating all browser windows crashed Chromium's GPU process and killed workers. WebGPU on OpenGL ES and no crash limit: 5 restarts, 0 crashes.
  • Opt-in, measured on L4Browser frame ticks staggered at 60 fpsEvery 60 fps browser window ticked at the same instant: a 2 ms spike of about 57 runnable threads per frame on 16 vCPUs, and a one-minute load average floating between 9 and 23 at 53 % CPU. With each worker at its own phase: peak 57 → 22.9, threads waiting for a CPU 4.55 → 1.30, 0 missed deadlines before and after.
  • Measurement methodMeasuring CPU pressure at 60 HzLoad average 25 on 16 vCPU at 69 % busy: ready-thread sampling, PSI and schedstat show one ~8 ms burst per 16.7 ms frame from ~6 threads per source. Later traced to the browser windows' frame clock, where it is a 2 ms spike.
  • LiveReal 1080p inputs, no shortcutsThe ground rule: every capacity-demo source is its own input of at least 1080p25, with its own media, processed on every frame.
  • LivePGM delay instead of a longer aux deadlineThe Program preview matches only its PGM pad one frame back, so its 100 source pads keep the normal 80 ms deadline.
  • LiveDSK fades in one passA key fades by weighting its alpha in the existing keyer pass: no second compositor, and frames without a fade run the old kernels.
  • LivePrewarmed DSK keysKeys stay subscribed while off, so a key cut or fade-in starts on the next program frame instead of 1–2 frames later.
  • LiveOne thread per GPU filter graphGPU and metadata-only filter graphs run on one thread instead of an idle 16-thread FFmpeg slice pool each.
  • LiveOne reference frame for monitor encodersAUX encoders keep one NVENC reference frame, because without B-frames each frame is predicted from the previous one.
  • LiveEvent-loop shardingSource pacing timers spread over four event-loop threads, reducing the modeled quadratic timer-work term across four shards.
  • LiveUnused GPU contextsRemoves an OpenGL context in every browser importer and a process-wide CUDA context. Both held memory and drew nothing.
  • Implemented; cadence GPU-testedNative input cadenceRetains realtime, removes 152 input FPS nodes in the captured show, and preserves fractional source periods with a 1/120000 time base.
  • LiveRaw uploads and the CUDA driver lockRaw NV12 and P010 frames go through a pinned buffer on the source’s own stream through patched FFmpeg filters; earlier traces implicated shared driver contention. The setup’s 110-input shows use it for 30 raw sources at 25 fps and 34 at 30. In the historical custom-node A/B at 68 inputs and 60 fps, hwupload missed 69 % of program deadlines; pinned missed 0.
  • LiveLooped clips keep counting across the wrapA looped file's next pass is shifted by the length of the one before, so timestamps keep rising and a wrap no longer costs the source a frame: about 0.9 drops/s per source with 2 s clips before.

Integration and validation scope

  • Built, Python tests pass; dedicated wipe GPU qualification pendingA wipe clip is cached whole or the start failsA stalled GPU upload on a fresh container was taken for the end of a clip: one wipe was stored with 2 frames instead of 120, the next with 129. A load now ends on the end-of-stream marker, its frame count is checked, and compiled CUDA kernels are kept on the media volume.
  • Implemented; primitive and mixer integration GPU smokes passcuda_transform, the shared geometry nodeOne CUDA frame in, one frame per output canvas, drawn by the compositors' own module; an output that would only repeat the input gets the input frame itself. Source transforms, catalogue normalization and resized renditions use it. GPU integration smokes pass; no full-show throughput comparison is claimed.
