Centred force_fps phase: jitter never flips frames

force_fps can shift a source's timestamps by one constant, picked so that its first frame lands exactly on an output tick. Small timestamp deviations then stay inside each frame's slot instead of pushing a frame onto a neighbouring tick, which could repeat one frame and drop another.

Status: Implemented, measuring

Why a source flipped between ticks

Every source except browser pages is paced by the same two nodes, built by _pace(): realtime with set_pts, then force_fps. realtime works on the host clock in whole milliseconds. On the first frame, and on each resync, it reads the clock and fixes an offset. Every later frame is stamped with its scheduled release time: the source timestamp minus that offset, rounded to a whole millisecond. A frame released late keeps its scheduled stamp, unless it is over 250 ms late, which makes realtime resync.

force_fps rounds each stamp to the nearest output tick. Where a source's frames fall between two ticks is set once, by when its realtime node synced, so it differs from source to source. In steady state a stamp deviates from even spacing only as much as the source's own timestamps do, plus the millisecond rounding: at 30 fps the 33.33 ms frame period becomes steps of 33, 34 and 33 ms, and at 60 fps steps of 17, 16 and 17 ms. At 25 and 50 fps the period is a whole number of milliseconds, so rounding adds no deviation.

When a source's frames sit within that fraction of a millisecond of the midpoint between two ticks, some round up and others down, in a pattern that repeats every three frames. A tick that gets no frame repeats the previous one, counted as duplicated. Of two frames on one tick, force_fps shows the first and holds the second. The next frame then replaces it unseen, counted as dropped. If the next tick is empty instead, the held frame fills it one tick late and neither is counted.

With center_phase, force_fps takes the first frame's distance from its nearest tick and subtracts it from every stamp. The first frame gets the same tick as before, and every later frame sits on a tick with half a frame of slack either way: 20 ms at 25 fps, 16.7 ms at 30 fps, 8.3 ms at 60 fps. Millisecond rounding no longer moves a frame across a slot edge. The constant is picked again after a discontinuity, after resetInput(), or when the input time base changes.

Measured before the fix

This was measured on a 30 fps show with 110 inputs on the 16 GB T4 test host: 36 NVDEC, 36 browser pages, 34 raw sources on the pinned upload chain and 4 key pages, all 1080p, with unique media per source. One of the 34 raw sources logged these force_fps statistics:

CounterValue
Frames in9,621
Duplicated3,214
Dropped3,205
Estimated input rate29.97 fps

The counters run from the node's start, not per 10 s. Frames arrived at the right rate, yet duplicates and drops were each almost exactly one in three of the frames in: about 10 of each per second at 30 fps (arithmetic from the counters). One duplicate and one drop every three frames is what the three-frame rounding pattern produces when it straddles a slot edge. That cause is an inference from the code, not a measurement.

After the fix: not measured yet. force_fps prints its statistics every 10 s once a source has duplicated or dropped any frame since it started. On the next run, a source that logs no statistics line has done neither.

At a glance

  • Whatforce_fps gains center_phase (bool, default false, so other graphs are unchanged). On the first frame it picks one constant, that frame's distance from its nearest output tick, and subtracts it from every input timestamp. It picks again after a discontinuity, resetInput() or a change of input time base. The mixer turns it on in _pace() for NVDEC and file sources, raw NV12/P010 (both upload chains) and v210. Browser pages are paced by smooth_timestamps and are unaffected. wipe_base_fps, wipe_rt_fps, and the record-output and Janus preview force_fps nodes keep the default.
  • WhyA source whose frames sat near the midpoint between two output ticks flipped between them. Before the fix, one raw source of 34 on the 30 fps show duplicated 3,214 and dropped 3,205 of 9,621 frames.
  • Latency0 frames added: no queue, buffer or wait, and frames leave force_fps when they did before. The first frame gets the tick nearest to it, as without center_phase, and later frames follow one tick per frame. Output timestamps change only where a frame used to flip.
  • Side effectsAt a discontinuity (a jump of more than one frame + 0.5 s, or backwards), the frame that jumped still uses the old phase and the frame after it picks a new one. The phase can move by up to a frame between those two, so one frame can be repeated or dropped there, once (from code). The playlist demo builds its clip chains with the same _pace(), so they get center_phase too.
  • Cost0 nodes, 0 queues, 0 threads. One timestamp subtraction per frame, plus two rescales each time the phase is picked. Code: +16/−1 lines in force_fps.cpp, +3/−1 in inputs.py (the flag and a two-line comment), one line in NODES.md and two test assertions.
  • RiskLow. Deviations of half a frame or more still duplicate or drop. The phase comes from one frame, with no averaging, so it is only as centred as that frame's own deviation: about 1 ms at most for millisecond rounding (estimate from code). A timeline shift smaller than one frame + 0.5 s keeps the old phase until the next discontinuity or resetInput(). One example is a realtime resync after a frame more than 250 ms late, which restamps from the clock. The change centres phase, not rate: a source whose real rate differs from the canvas still has to duplicate or drop.
  • Switch it offDelete "center_phase": True in _pace() in pyplumber/mixer/inputs.py. There is no runtime switch.
