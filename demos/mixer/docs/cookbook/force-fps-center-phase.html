Native input cadence without force_fps

Reviewed 2026-10-06 against mixer-improv at d1dc35fa. Measurements retain their original workload and validation scope; this review does not certify a running deployment.

File inputs keep their source cadence. The clocked compositor chooses frames for the canvas rate; input realtime remains in place. Output and AUX rate normalization remain.

Current graph and scope

decode / raw upload → realtime → colour where required → fan-out → clocked compositor

The mixer calls the shared input builders with native_rate=True. Their default remains the normalized realtime → force_fps chain for playlist and other users. Browser sources still use smooth_timestamps and repeat_last_frame.

The existing realtime node uses tick_period="1/30000" without a tick source, selecting a 1/120000-second timestamp time base while retaining wallclock pacing. Frame periods for 24000/1001, 30000/1001 and 60000/1001 are exact in that time base. The mixer explicitly passes 0.25 seconds negative-time tolerance and a 1-second discontinuity threshold so the finer time base does not change these durations. No realtime C++ behavior or shared helper default changed.

Saving in the 188-source configuration

The captured show had 120 encoded sources, 32 raw sources, 36 browser sources and four additional browser keys. Removing the 152 file-input FPS nodes saves 152 nodes and 152 queues. They shared event loops, so this does not remove 152 threads. See sharding and colour-tag bypass for the remaining reductions.

GPU correctness test, 2026-10-06

Eight independent 320×180 barcoded CUarray inputs ran at 25, 30, 30000/1001, 469/20 (23.45), 50, 24000/1001, 60000/1001 and 120 fps, looping every 12 seconds. Program and full-rate AUX encoded 1280×360 at 60 fps.

  • 120.3667 seconds of steady output: 7,223 frames per output, all 7,222 timestamp steps exactly 1/60 second.
  • All 29 checks passed, covering cadence, phase bounds, four cuts, a one-second source stall, resumed motion and bounded queues.
  • The 60000/1001 input repeated seven frames and skipped none; the 120 fps input advanced by two source frames per canvas tick.
  • p95 output-PTS-to-diagnostic-observation age: 52.27 ms program, 52.12 ms AUX. This includes diagnostic GPU download and is neither source-to-output nor command-to-picture latency.

The test used native code at 9f940e44 and Python pacing at d577a12d, before subsequent source-routing and colour-tag changes. This small fixture establishes cadence correctness, not 188-source capacity. Captured report and revision scope.

Why this replaces the old phase recipe

This URL previously documented force_fps.center_phase. It remains useful in normalized chains: one constant aligns the first timestamp to an output tick, avoiding rounding-induced repeat/drop pairs. A historical 110-input 30 fps T4 run recorded 3,214 duplicates and 3,205 drops over 9,621 frames on one raw input before that fix. Those counters are not a measurement of the current native-rate chain.

A first removal prototype retained millisecond timestamps and introduced extra repeat/drop pairs at 60000/1001. The finer realtime time base resolved that regression. Do not remove the precision settings when removing FPS nodes.
