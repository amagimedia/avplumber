Raw uploads and the CUDA driver lock

With FFmpeg hwupload, each raw NV12 source uploads its frames with a slow, synchronous copy that holds a lock the whole mixer shares; copying through a reusable pinned buffer on the source's own stream should shrink that hold to a short enqueue.

What changes in the graph

At a glance

  • What

    Swap the FFmpeg hwupload filter for raw_to_cuda, a generalization of the existing v210_to_cuda node. Per frame: one copy into a reusable pinned buffer, cuMemcpy2DAsync on the source's own non-blocking stream, then a stream sync before the frame moves on. Consumers are unchanged.

  • Why

    The hwupload copy is synchronous, from pageable memory, on the default stream. The driver bounces it through its own pinned buffer (a second CPU copy) and holds the context lock for the whole transfer. Every other CUDA call in the process (compositors, DMA-BUF imports, other uploads, encoders) needs that lock.

    With hwupload at 100 live sources the GPU engines were fine (SM 56 %, NVDEC 81 %, NVENC 32 %, VRAM 9.6 of 15.4 GB). The CPU threads were not: 28 upload threads at 81 % CPU, 68 input threads at 94 %.

  • Latency

    Expected neutral or better; the 60 fps A/B against hwupload measured deadlines, not latency. Program: no frame added. The frame is already on the GPU when pacing releases it, so the upload leaves the release path.

    The one uploaded frame queued ahead of pacing is prefetch, not an extra frame of delay. Command-to-screen: unchanged (an input-side change).

  • Side effects
    • About 100–175 MB more VRAM at 28 sources.
    • The raw chain shrinks from 7 to 5 nodes.
  • Cost
    • Nodes: raw_to_cuda replaces the hwupload filter node one for one. The rawvideo decoder and setpts filter drop out, so 7 → 5 per raw source; queues shrink with them. No new threads.
    • Code: about 130 lines, sharing the upload path of v210_to_cuda.
    • Host RAM: one pinned 3.1 MB buffer per source, about 87 MB for 28 (computed, not measured).
    • CPU: one copy per frame instead of two. PCIe: same bytes.
  • Risk

    Shown to matter at 60 fps; the mechanism is still inferred from traces. The traces show contention and the 60 fps run shows the outcome, not which part of the change (pinned staging, the private stream, or the two dropped nodes) removes the stall. The source thread still blocks on its own stream sync each frame. Before its first write into the frame, the private stream waits on the GPU for work already queued on the shared device stream (PacketToCuda::waitForReaders()), so it is not fully decoupled. raw_to_cuda waits before its copy; v210_to_cuda waits only between the staging copy and the unpack kernel, so the copy overlaps. Pinned memory is locked RAM the OS cannot page out.

  • Switch it off

    The library default is canvas.raw_upload: "hwupload" (vanilla FFmpeg), so a config that does not set it is unchanged. The setup's base recipe, demo.example.json, sets "pinned", so every show the setup builds uploads through raw_to_cuda; set it back to "hwupload" there.

Why it matters at 110 sources

The setup's 110-input shows carry 40 NVDEC + 40 browser windows + 30 raw sources at 25 fps, and 36 + 40 + 34 at 30 fps; the browser windows include 4 key pages (Rate-aware capacity budgets). Raw uploads grow from 28 sources at 2.2 GB/s to about 2.3 GB/s at 25 fps and about 3.2 GB/s at 30 fps (computed: raw upload units × 3.1 MB × frame rate, where a P010 source counts as 2 units). The PCIe link has headroom; the lock is the limit. The evidence from lighter load: a pinned compositor table upload took 0.081 ms with 14 raw uploads and 5.31 ms with 28, 98–99.7 % of it in futex waits, while the compositor and import cleanup waited on the same futex.

With pinned uploads at 30 fps and 110 inputs, the upload threads still waited on a lock for 2.2 s per 10 s. There is no hwupload run at the same load, so that figure does not yet say how much pinned helps.

How it gets measured

The 60 fps run above shows the outcome, not the mechanism. Still pending: an A/B at 110 sources, hwupload vs. pinned, same build.

  • Futex wait time of compositor, import and upload threads.
  • Scheduler run delay from /proc/<pid>/task/*/schedstat.
  • CUDA API durations in an Nsight Systems (nsys) trace.

Follow-ups, only if needed: read files straight into pinned memory (drops the remaining CPU copy); set the CUDA context once per thread instead of per frame; one upload worker instead of one per source.

Not allowed: caching looped clips on the GPU. That is cheating: it hides the upload cost instead of fixing it.
