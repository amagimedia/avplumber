Pinned raw uploads through FFmpeg

Reviewed 2026-10-06 against mixer-improv at d1dc35fa. Measurements retain their original workload and validation scope; this review does not certify a running deployment.

Raw NV12, P010 and v210 enter CUDA through patched FFmpeg filters. The former raw_to_cuda and v210_to_cuda nodes have been removed.

Current mixer chains

Pinned NV12/P010 (5 nodes):
input_rec → demux → dec_video → filter_video(hwupload_cuda=pinned=1[,setparams]) → realtime

Vanilla NV12/P010 (6 nodes):
input_rec → demux → dec_video → filter_video(setpts) → realtime → filter_video(hwupload[,setparams])

These counts cover input construction, before mixer colour conversion and fan-out. Shared builders used without native_rate=True add one force_fps node. The v210 path decodes packed bytes as raw video and uses hwupload_cuda=v210_width=... to upload/unpack them. Declared YUV tags are stamped in the existing upload graph, enabling the guarded colour-node bypass.

The pinned filter stages host data in page-locked RAM, uses a private CUDA stream, and hands downstream a completed CUDA frame. Raw CPU-to-GPU ingestion is the upload boundary; subsequent GPU processing stays on the GPU. This does not cache looped input frames on the GPU or skip source work.

Configuration and dependencies

canvas.raw_upload defaults to hwupload in the library; the example recipe selects pinned. Patched FFmpeg 9 provides the pinned uploader, v210 unpacking and RGBA support. Keep the FFmpeg 8 and 9 patch sets separate; consult the dependency guide for the selected build.

Historical performance evidence

The custom-node-era 68-input T4 A/B used 18 NVDEC, 29 browser, 17 raw NV12 and four browser keys at 60 fps on 16 vCPUs. Vanilla upload missed 69% of program deadlines; pinned upload missed none. NVDEC utilization rose from about 26% to 85% as the pipeline stopped stalling. These figures establish the original motivation, not a new benchmark of the replacement FFmpeg implementation.

Earlier traces showed shared futex waits in upload, import and compositor threads: a compositor table upload rose from 0.081 ms with 14 raw uploads to 5.31 ms with 28. A shared CUDA-driver lock is an inference from those traces, not identification of a particular internal NVIDIA mutex. A matched large-show A/B of the replacement remains to be done.

Current validation

2026-10-06 GPU smoke tests passed byte-exact NV12/P010 uploads in pinned and vanilla modes, plus v210 widths 48, 50 and 1920, with both normalized and native input pacing. Those checks preceded the latest colour-tag bypass. They establish data/cadence correctness, not a new source-capacity ceiling.

Single-thread GPU filter graphs avoid slice-thread pools. The upload still costs host reads, staging copies, a GPU transfer and synchronization. Reverting to hwupload changes that path; it does not remove raw ingestion cost.
