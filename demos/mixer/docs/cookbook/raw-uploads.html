Raw uploads and the CUDA driver lock

Each raw NV12 source uploads its frames with a slow, synchronous copy that holds a lock the whole mixer shares; copying through a reusable pinned buffer on the source's own stream should shrink that hold to a short enqueue.

Status: Opt-in, pending measurement

What changes in the graph

At a glance

  • What

    Swap the FFmpeg hwupload filter for raw_to_cuda, a generalization of the existing v210_to_cuda node. Per frame: one copy into a reusable pinned buffer, cuMemcpy2DAsync on the source's own non-blocking stream, then a stream sync before the frame moves on. Consumers are unchanged.

  • Why

    Today's copy is synchronous, from pageable memory, on the default stream. The driver bounces it through its own pinned buffer (a second CPU copy) and holds the context lock for the whole transfer. Every other CUDA call in the process (compositors, DMA-BUF imports, other uploads, encoders) needs that lock.

    At 100 live sources the GPU engines are fine (SM 56 %, NVDEC 81 %, NVENC 32 %, VRAM 9.6 of 15.4 GB). The CPU threads are not: 28 upload threads at 81 % CPU, 68 input threads at 94 %.

  • Latency

    Expected neutral or better; not yet measured. Program: no frame added. The frame is already on the GPU when pacing releases it, so the upload leaves the release path.

    The one uploaded frame queued ahead of pacing is prefetch, not an extra frame of delay. Command-to-screen: unchanged (an input-side change).

  • Side effects
    • About 100–175 MB more VRAM at 28 sources.
    • The raw chain shrinks from 7 to 5 nodes.
  • Cost
    • Nodes: raw_to_cuda replaces the hwupload filter node one for one. The rawvideo decoder and setpts filter drop out, so 7 → 5 per raw source; queues shrink with them. No new threads.
    • Code: about 130 lines, sharing the upload path of v210_to_cuda.
    • Host RAM: one pinned 3.1 MB buffer per source, about 87 MB for 28 (computed, not measured).
    • CPU: one copy per frame instead of two. PCIe: same bytes.
  • Risk

    Unproven: the traces show contention, not that pinned staging and a private stream remove it. The source thread still blocks on its own stream sync each frame. Before its first write into the frame, the private stream waits on the GPU for work already queued on the shared device stream (PacketToCuda::waitForReaders()), so it is not fully decoupled. raw_to_cuda waits before its copy; v210_to_cuda waits only between the staging copy and the unpack kernel, so the copy overlaps. Pinned memory is locked RAM the OS cannot page out.

  • Switch it off

    Off by default: canvas.raw_upload is "hwupload" (vanilla FFmpeg). "pinned" opts in, and is set only for the 110-source A/B test. It becomes the default only if it clearly removes the stall with no latency cost; otherwise the node is deleted.

Why it matters at 110 sources

With NVDEC fixed at 40 and browsers at 32, raw uploads grow from 28 to 38, from 2.2 to about 3.0 GB/s. The PCIe link has headroom; the lock is the limit. The evidence from lighter load: a pinned compositor table upload took 0.081 ms with 14 raw uploads and 5.31 ms with 28, 98–99.7 % of it in futex waits, while the compositor and import cleanup waited on the same futex.

How it gets measured

A/B at 110 sources, hwupload vs. pinned, same build.

  • Futex wait time of compositor, import and upload threads.
  • Scheduler run delay from /proc/<pid>/task/*/schedstat.
  • CUDA API durations in an Nsight Systems (nsys) trace.

Follow-ups, only if needed: read files straight into pinned memory (drops the remaining CPU copy); set the CUDA context once per thread instead of per frame; one upload worker instead of one per source.

Not allowed: caching looped clips on the GPU. That is cheating: it hides the upload cost instead of fixing it.
