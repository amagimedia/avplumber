Implementation links checked 2026-10-09 against develop at c20464a5; mixer code is unchanged from the 2026-10-06 review. Measurements retain their original workload and scope. Watch the current 192-input L4 demo.

Current scope. Current file-source pacers are realtime only; browser smooth_timestamps remains. The captured 188-source show plus four keys maps to 38 realtime + 10 browser pacers per shard: 48 nodes instead of 86. Four shards remain; removing 152 FPS nodes does not remove 152 threads. The default loop retains output/AUX and wipe pacing.

Split the sources' pacing timers across four event-loop threads, so one thread no longer wakes for every source and rescans every source on each wake-up.

Status: Implemented

Why one loop costs N²

An event loop sleeps in poll() until its next timer or a watched file descriptor fires. Two things grow with the number of sources N on one loop:

Wake-ups per second grow with N. Each source's pacing nodes set their own timers.

Work per wake-up grows with N. Each wake-up rebuilds the pollfd array for every watched fd, and each new timer walks the sorted timer list to find its slot.

So one loop's cost grows with N². Four loops each carry N/4 sources: (N/4)² = N²/16 per loop, which is 16× less on the busiest core. Summed over the 4 loops it is 4 · N²/16 = N²/4, which is 4× less CPU in total.

Measured on the T4 test host with 100 sources on one loop: 43 % of one core and 924 wake-ups per second.

At a glance

  • WhatSource i's pacing nodes (realtime; smooth_timestamps for browser sources) join event loop pacing_{i % 4} through the existing event_loop node parameter. Output, aux and wipe pacing stay on default.
  • WhyOne loop for 100 sources used 43 % of a core at 924 wake-ups/s, its modeled scaling term grows as N², and one slow timer delays every source behind it.
  • Latency0 frames added to program and to command-to-screen latency: no new queue, buffer or node. What changes is timer lateness: one busy loop delayed realtime's timestamps and held decoders; four loops cut that delay. The improvement is not measured yet.
  • Side effectsSources on different loops now run their pacing callbacks in parallel, not one after another. Output, aux and wipe pacing get the default loop to themselves, so source timers no longer queue in front of them.
  • Cost0 nodes, 0 queues, 0 VRAM, 0 framework lines. 4 new event-loop threads (pacing_0…pacing_3): source pacing moves from 1 thread to 4. Code: one constant, a two-line helper and an event_loop argument passed through the input builders.
  • RiskLow. Sources were never phase-locked to each other, so moving them to separate threads changes no ordering a source relies on.
  • Switch it offSet PACING_LOOPS = 1. All sources then share pacing_0. That is not the old layout exactly: output, aux and wipe pacing still keep default to themselves.

Where in the code

  • src/EventLoop.hpp: each wake-up rebuilds the pollfd array for every watched fd.
  • src/EventLoop.hpp: schedule() walks the sorted timer list to insert each timer.
  • src/graph_mgmt.cpp: the existing event_loop node parameter picks a named loop.
  • pyplumber/mixer/application.py: PACING_LOOPS = 4 and _pacing_loop().
  • pyplumber/mixer/inputs.py: _pace() passes event_loop to realtime; normalized helper callers retain force_fps.center_phase (Native input cadence).
  • pyplumber/mixer/dmabuf_inputs.py: browser sources pass it to smooth_timestamps.
