Browser CPU is per painted frame

Chromium's cost for a browser window follows the frames the window delivers, not what the page shows: about 3.5 ms of CPU for every painted frame, spread over the renderer, the GPU process and the browser's main process, about 0.2 core per window at 60 paints a second. The demo's browser test page slid its marker without pause, so all 29 windows painted at 60 fps. It now rests 4 s and slides 2 s, as a real graphic does, each window from its own point of the cycle; and the browser image moved from Electron 41 to 44.5.1. Electron went from 5.90 to 2.83 cores and host idle from 28 to 50 % on the 68-input 60 fps show.

Where a window's CPU goes

For every frame a window delivers, three Chromium processes do work: the renderer paints the damaged page (about 3 % of a core per window at 60 paints/s), the GPU process composites it in VizCompositor and draws through ANGLE's GL (about 12 %), and the browser's main process handles the paint event, passes the DMA-BUF descriptor over the socket and takes the mixer's release ack (about 6 %; see Browser frame hand-off). Together about 3.5 ms of CPU per delivered frame, which at 60 paints/s is about 0.2 core per window (3 + 12 + 6 % = 21 %, computed). The cost tracks delivered frames, not page complexity.

Chromium paints only on damage, so a page that does not change delivers no frame and costs next to nothing. On the same show a static key page painting 3 times a second took about 7 % of a core, and the always-sliding test page at 60 paints/s 21–25 %. The number of Electron workers does not enter: the work is per window per frame, so grouping windows into fewer, bigger workers would not reduce it and would concentrate VizCompositor load in fewer GPU processes (rejected idea 9). That leaves two levers, and this page pulls both: fewer delivered frames when nothing on the page moves, and a cheaper Chromium.

This is not the shortcut the cookbook rules out. Every window is still an independent 60 fps input: while its marker moves it paints 60 frames a second and the mixer imports, stamps and composites every one; the sender, the chain and the ring are unchanged. What changed is the content: a graphic that holds still two thirds of the time, which is what real lower thirds, bugs and tickers do. Running browser sources at 30 fps in a 60 fps show, which halves the delivered rate of a page that is moving, stays rejected (idea 10).

What changed

  1. The test page rests two thirds of the time. Before, the marker of browser_alpha.html ran a CSS keyframe animation, 4 s each way, without pause, so every window painted every frame. Now the marker's transform has a 2 s transition, and a timer toggles its target every 6 s: slide 2 s, rest 4 s. It moves on transform, not left, which snaps to whole pixels and lays out on the main thread each frame. Each window starts its cycle at (index × 0.618 mod 1) × 6 s, where index is the number in the source's id (browser_007 is 7), which prepare_demo embeds in the page as a data attribute; golden-ratio steps spread any count of windows evenly over the cycle, so 9–11 of the 29 slide at any moment instead of all of them. Paints fell from 1,748 to 594 a second, Electron from 5.90 to 3.25 cores, avplumber from 5.08 to 4.61, GPU utilisation from about 83 to 62 %, host idle rose from 28 to 49 %, with 0 missed program deadlines.
  2. Electron 44.5.1 (Chromium 152) on Fedora 44. Electron 41 (Chromium 146) and Fedora 42 were both end of life. On the rested page, Electron CPU fell from 3.30 to 2.83 cores (−14 %), host idle rose from 47.7 to 50.3 %, avplumber went from 4.62 to 4.58 cores and CPU pressure (PSI some) from 17.6 to 16.4 %, with no regression. Electron 42 and later no longer download the Electron binary in the package's npm postinstall, so the image build runs node node_modules/electron/install.js after npm ci. The image needs only Electron's runtime libraries; the NVIDIA userspace comes from the host through the container runtime. The GPU-process crash on recreating all windows is the same on Electron 41 and 44; its fix is on Keeping Vulkan out of the GPU process.

At a glance

  • What

    Two changes outside the mixer. The demo's browser test page, demos/mixer/browser_alpha.html, rests 4 s and slides 2 s, each window from its own point of the cycle. The browser image builds Electron 44.5.1 on Fedora 44. No avplumber, mixer Python or browser-sender change.

  • Why

    With the always-sliding page, 29 windows painting 60 times a second made Electron the largest CPU consumer of the 60 fps show: 5.90 cores against avplumber's 5.08, the host 28 % idle and the GPU at about 83 %. Chromium's work is per delivered frame, so the page had to deliver fewer frames when nothing moves, and Chromium had to get cheaper for the frames it does deliver.

  • Latency

    0 frames added: nothing in the frame path changed, the same sender, chain, ring and paint numbering (Browser paints numbered on the canvas grid). A resting page delivers no paint; the compositor repeats its last frame for that tick, as it does for any still key page. The marker moves on a compositor transform, so its motion is not delayed by main-thread layout. Cut and program latency were not re-measured in these runs.

  • Side effects

    The demo's browser tiles hold still two thirds of the time, so the demo shows less motion than before, and a browser-heavy scene loads the browser path less than the always-sliding page did: on average about 20 paints/s per window (594 over 29, computed) instead of 60. Every window is still a 60 fps input while it moves.

    Electron 44 is six Chromium majors up from 41 (146 → 152). Behaviour changes ride along; the one met so far, the GPU-process crash when all windows are recreated, exists on both versions and has its own page.

  • Cost
    • 0 nodes, 0 queues, 0 new threads; VRAM not re-measured.
    • Code: +15/−5 lines in the test page; 1 line in package.json and its lockfile; +2/−1 and 2 changed lines in the Dockerfile.
    • One browser image rebuild; the Electron binary is fetched by the explicit install.js step.
  • Risk

    Low. The per-process split (3, 12 and 6 %) and the paint-rate costs are from one host and one show. The −14 % from Electron 44 is one pair of runs, with about 0.05 core of run-to-run noise on the baseline. An image build that drops the install.js step has no Electron binary, since Electron 42 and later no longer fetch it in postinstall. Nothing on this page changes what the mixer does with a frame.

  • Switch it off

    No runtime switch; the two are independent. Restore the marker's animation: slide 4s linear infinite alternate and its keyframes in browser_alpha.html: every window then paints at 60 fps again. Pin "electron" in deps/dma-browser/package.json back to 41.3.0 and rebuild the browser image.
