Colour tags at the fan-out

Measured on 2026-10-13 on the 16 vCPU L4 host that runs the demo. Source links are pinned to develop at 8fa15c92. Watch the current 192-input L4 demo.

A source whose declared colour already matches the canvas needs its frames tagged and nothing else. It used to get a filter node for that, with a thread that took every frame from one queue and put it on the next. The fan-out every source has anyway now stamps the tags, and such a source has no colour filter.

Status: Live

What

one_to_many takes frame_color: an object of colour fields (color_trc, color_primaries, colorspace, color_range, alpha_mode) that it writes on every video frame before handing it out. The mixer works out each source's colour stage as before. When that stage would be the source's setparams expression and nothing more, the mixer gives the tags to the source's fan-out and builds no filter. Sources that share one input edge get them from the fan-out that splits the edge.

Which sources

  • Browser sources. Their colour stage only ever tagged, the premultiplied-alpha tag included; the compositor reads packed RGB itself.
  • Decoded sources that declare a colour matching the canvas and a decoded_format (nv12 or p010le) equal to the canvas storage. Setup's generated clips declare it.
  • Raw NV12, P010 and v210 sources arrive tagged: the upload stamps the declared tags, and raw_video_file_cuda takes frame_color as the fan-out does. They had no colour filter before this change either.

What changed on 2026-10-13

Until then only raw sources went without the node; every browser and decoded source kept a filter graph that did nothing but tag. On the 192-source SDR show at 1080p30 the change removed 141 colour threads, and the mixer went from 1,472 to 1,327 threads. No frame is added or delayed: a frame passes one queue and one thread fewer on its way to the compositors. Setup's start check accepts a running fan-out in place of a colour filter that does not exist; a colour filter that exists and is not running still fails the start.

What keeps a colour filter, and how to get one back

  • A source that converts: another colour space or transfer, a tone map, or a storage format other than the canvas's.
  • A decoded source without decoded_format. Its storage is then known only per frame, and the filter converts when it must. Declare decoded_format only for media whose depth is known; it is not accepted together with a source filter.
  • A source with no declared colour or with a user filter: the stage reads each frame's own tags.
  • Routed --input sources: their colour stage sits after the router, once per slot.

There is no switch. Leaving decoded_format out of a decoded source brings its colour filter back.

Where in the code

  • src/frame_color_tags.hpp: the fields and their names. src/nodes/one_to_many.cpp: frame_color on the fan-out.
  • pyplumber/mixer/graph.py: _prepare_source_edges and _frame_color decide, _color_edge builds the filter where one is needed.
  • pyplumber/mixer/config.py: decoded_format. demos/mixer/prepare_demo.py sets it for generated clips. pyplumber/mixer/application.py: which sources are registered as already tagged, and with which storage.
  • pyplumber/mixer/gui/setup_runtime.py: the start check.
  • Tests: tests/test_mixer_color.py (which sources get the tags, and that no colour node is built for them), tests/cpp/test_frame_color_tags.cpp (the field parser).
  • Docs: config.md · sources lists decoded_format.
