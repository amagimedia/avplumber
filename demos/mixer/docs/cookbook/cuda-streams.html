AVPlumber · Mixer optimization cookbook

One main CUDA stream, one per monitor

The program runs on one CUDA stream; each aux monitor gets its own non-blocking stream in the same CUDA context, so a slow monitor cannot hold up the program or the other monitor.

Status: Live

At a glance

  • What

    Almost all mixer GPU work (NVDEC output copies, scaling and format conversion, browser page imports, M/E compositors A and B, wipe, keyer, program and clean encoders) runs on the default stream of the mixer_gpu context. Each aux monitor wraps the same context with its own non-blocking stream, publishes it as aux_<id>_gpu, and runs its compositor, colour conversion and NVENC encoder on it.

  • Why

    Non-blocking means no implicit ordering: the default stream does not wait for an aux stream, and an aux stream does not wait for the default stream. A slow monitor cannot stall the program or the other monitor. Sharing the context avoids the memory of a second context: about 200 MB (estimate).

  • Latency

    Program and command-to-screen: 0 frames added, by construction, not measured. The program stream never waits for an aux stream. On one shared stream, a slow monitor frame would queue ahead of the next program tick instead. Monitors: the stream split adds no wait of its own.

  • Side effects

    Streams isolate waiting, not capacity: every stream shares the same GPU engines and NVENC. Any FFmpeg filter fed aux frames inherits the aux stream automatically, because FFmpeg uses the stream of the frames' device. Tearing down an aux bus synchronizes and destroys its stream.

  • Cost

    One CUDA stream and one CUDA event per aux bus (two buses in the demo). No extra nodes, queues or threads. One 33-line header. No extra context VRAM. CPU: each aux frame ends with a cuStreamSynchronize on the aux stream only.

  • Risk

    Because nothing is ordered implicitly, an aux reader must wait for its inputs explicitly. The aux compositor records an event on each input's producer stream and makes its own stream wait on it; the program stream is never synchronized. A new aux consumer that skips this wait could read a half-written frame.

  • Switch it off

    No runtime switch. Without aux_buses no aux stream exists. Running the aux path on the default stream is a code change: stop wrapping the device in aux_mode.

Why not a stream per node?

About 800 nodes' GPU work sharing one stream is not the bottleneck by itself. The measured limit at high source counts was CPU-side CUDA submission contention triggered by raw uploads, not stream ordering; see Why uploads limit this mix.

Raw uploads are the other exception to the single stream. v210_to_cuda (4:2:2 raw) creates a private non-blocking stream per source and synchronizes it before publishing, so consumers get a complete frame. raw_to_cuda (NV12 and P010 raw) does the same with canvas.raw_upload: "pinned", which every show the setup builds uses. With the library default, "hwupload", NV12 and P010 upload through FFmpeg hwupload on the default stream; see Raw uploads.
