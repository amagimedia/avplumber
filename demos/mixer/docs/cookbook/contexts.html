Unused GPU contexts

Implementation links checked 2026-10-09 against develop at c20464a5; mixer code is unchanged from the 2026-10-06 review. Measurements retain their original workload and scope. Watch the current 192-input L4 demo.

Current scope. Unused context removal remains in place. The custom v210 uploader was replaced by FFmpeg; it is no longer a CUDAState flag reader. Memory figures below are historical estimates, not a new VRAM measurement.

Two GPU contexts held device memory but drew nothing: an OpenGL context in every browser importer, and a CUDA context created at process start. The mixer image removes both and runs live on the test host. A code audit of the other apps that use avplumber found nothing that relied on either context.

Status: Implemented

1. The GL context in each browser importer

Each browser page has its own drm_prime_to_cuda node. The setup allows up to 40 browser pages at every frame rate (five browser workers of eight windows); the memory figures on this page were estimated for 32. Importing a page frame needs only an EGL display: eglCreateImage already takes EGL_NO_CONTEXT, and CUDA registers the EGL image directly. The node still created an OpenGL context and a 2×2 pbuffer, and made it current before every import. Nothing drew with it. Both importers, drm_prime_to_cuda and drm_prime_to_egl_image, now share one display-only setup, EglDmabufDisplay.

2. The global CUDA context

A constructor in src/cuda.cpp ran at process start and created a CUDA context on device 0. Every CUDA node runs in the context of its hwaccel device instead. The only thing other code read was the has_errors flag, which does not need a context. A later cleanup also dropped CUDAState::device, which nothing read once the context was gone: start-up now only counts devices, and CUDAState holds just has_errors.

At a glance

  • Whatdrm_prime_to_cuda keeps only an initialized EGL display: no GL context, no pbuffer, no eglMakeCurrent per import. init_global_cuda stops calling cuCtxCreate; it only counts devices and sets the error flag, and CUDAState no longer has a device field.
  • WhyNeither context drew anything, but each held device memory. The importer's context existed once per browser page: 32 times in the show it was estimated for, up to 40 in the setup's 110-input shows. drm_prime_to_egl_image already imports the same DMA-BUFs without a GL context.
  • Latency0 frames on program and on command-to-screen: neither context sat on the frame path. Each new DMA-BUF import (a cache miss, not every frame) skips one eglMakeCurrent call on the CPU; not measured.
  • Side effectsLess VRAM held per process, so more headroom for browser pages and compositors. No thread has a CUDA context current at start any more: code that called CUDA without binding its hwaccel context would now fail instead of running on the hidden global one. The start-up error log reads "failed to find a CUDA device".
  • Cost0 nodes, 0 queues, 0 threads. Net −84 lines (13 added, 97 removed). Frees an estimated ~150 MB (100–250 MB, unmeasured) across 32 importers, about 190 MB for 40 if it scales in proportion (also an estimate), plus 60–100 MB (estimate) for the global context. One fewer eglMakeCurrent per import on the CPU; GPU work unchanged.
  • RiskBoth files are shared avplumber code that other apps use. The code audit of those apps (below) found nothing that relied on the global context being current on the loading thread, and no GL call remains in the importer, including the zero_copy path. A smoke run of those apps after they bump avplumber is still pending.
  • Switch it offThere is no runtime flag; the code is deleted. Reverting means restoring the removed lines and rebuilding. If that smoke run finds a behaviour change, the removals get gated behind an option or dropped.

Where in the code

  • src/nodes/hwaccel/EglDmabufDisplay.hpp: the display-only setup both importers share; the comment explains why.
  • src/nodes/hwaccel/drm_prime_to_cuda.cpp: ensureEGL opens it.
  • drm_prime_to_cuda.cpp: eglCreateImage with EGL_NO_CONTEXT; source registers the image with CUDA in the hwaccel context.
  • drm_prime_to_cuda.cpp: the destructor; the display is process-global and never terminated.
  • The other importer: src/nodes/hwaccel/drm_prime_to_egl_image.cpp and source, the same display-only import.
  • src/cuda.cpp: no context and no device handle at start, only cuDeviceGetCount and has_errors; src/cuda.hpp: CUDAState holds only has_errors.
  • Current flag readers: cuda_to_egl_image.cpp, nvof_fruc.cpp.
  • Docs: NODES.md · drm_prime_to_cuda; the browser window counts are in capacity.md · Mixer demo capacity; docker-compose/mixer/compose.yaml sets 40 windows, eight per worker (Source limits by mode and frame rate).

Historical deployment note. Compatibility audit (2026-10-01): eka-recorder-ai and sports-live-reframer pin avplumber as a submodule, their CUDA nodes make their own hwaccel context current before any CUDA call, none reads the removed global_cuda fields, and their runtime Python runs no CUDA of its own. A smoke run of both after they bump avplumber remains the final check. Source links above identify the reviewed revision.
