Unused GPU contexts

Two GPU contexts held device memory but drew nothing: an OpenGL context in every browser importer, and a CUDA context created at process start. This branch removes both; the removal stays only if a compatibility audit shows no behaviour change for other apps.

Status: Implemented, not deployed Compatibility audit pending.

1. The GL context in each browser importer

Each browser page has its own drm_prime_to_cuda node; the demo runs 32. Importing a page frame needs only an EGL display: eglCreateImage already takes EGL_NO_CONTEXT, and CUDA registers the EGL image directly. The node still created an OpenGL context and a 2×2 pbuffer, and made it current before every import. Nothing drew with it. Both importers, drm_prime_to_cuda and drm_prime_to_egl_image, now share one display-only setup, EglDmabufDisplay.

2. The global CUDA context

A constructor in src/cuda.cpp ran at process start and created a CUDA context on device 0. Every CUDA node runs in the context of its hwaccel device instead. The only thing other code read was the has_errors flag, which does not need a context. A later cleanup also dropped CUDAState::device, which nothing read once the context was gone: start-up now only counts devices, and CUDAState holds just has_errors.

At a glance

  • Whatdrm_prime_to_cuda keeps only an initialized EGL display: no GL context, no pbuffer, no eglMakeCurrent per import. init_global_cuda stops calling cuCtxCreate; it only counts devices and sets the error flag, and CUDAState no longer has a device field.
  • WhyNeither context drew anything, but each held device memory. The importer's context existed 32 times, once per browser page. drm_prime_to_egl_image already imports the same DMA-BUFs without a GL context.
  • Latency0 frames on program and on command-to-screen: neither context sat on the frame path. Each new DMA-BUF import (a cache miss, not every frame) skips one eglMakeCurrent call on the CPU; not measured.
  • Side effectsLess VRAM held per process, so more headroom for browser pages and compositors. No thread has a CUDA context current at start any more: code that called CUDA without binding its hwaccel context would now fail instead of running on the hidden global one. The start-up error log reads "failed to find a CUDA device".
  • Cost0 nodes, 0 queues, 0 threads. Net −84 lines (13 added, 97 removed). Frees an estimated ~150 MB (100–250 MB, unmeasured) across the 32 importers, plus 60–100 MB (estimate) for the global context. One fewer eglMakeCurrent per import on the CPU; GPU work unchanged.
  • RiskBoth files are shared avplumber code that other apps use. The change stays only if a compatibility audit shows no behaviour change: the other apps' tests pass and every browser page still imports. Two checks belong in that audit: nothing relied on the global context being current on the loading thread, and no GL call remains in the importer (none does today, including the zero_copy path).
  • Switch it offThere is no runtime flag; the code is deleted. Reverting means restoring the removed lines and rebuilding. If the audit finds a behaviour change, the removals get gated behind an option or dropped.
