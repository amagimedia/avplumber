6. Bound browser allocations and release leases after one copy

Stock Chromium plus the allocation shim remains the default. The optional exporter can keep a fixed prewarmed pool while AVP owns its downstream frames.

Reviewed 15 October 2026 against e72ff8b4. These pages describe that code and named workload settings; they do not assert what every deployment runs.

Two supported paths, different retention rules

Path Allocation and return policy
Stock Electron/Chromium + shim ringSize bounds sent-but-unacknowledged frames, not Chromium allocations. Return pacing avoids bursts that churn Chromium's idle-buffer cache.
Optional fixed-pool exporter + AVP copy Producer allocations are fixed. AVP prewarms and retains all imports, copies each frame into owned CUDA memory, and returns the Chrome lease after the copy. No extra return queue.

The default install downloads stock Electron. Setting a ring size alone does not turn its capture allocation pool into a fixed pool. The optional build needs the exporter patches and a compatible resources/avp-capture-pool.json manifest.

Nine is the tested starting point for the optional build

DMA_BROWSER_CHROMIUM_EXTRA_FEATURES=AvpZeroCopyOffscreenExport:buffers/9,RenderableMappableSharedImageForceScanout
AVP_BROWSER_COPY_ON_IMPORT=1

Only a version-2 manifest with the startup-size patch supports a chosen size from 2 to 16. Version 1 describes the hardcoded eleven-buffer binary. The service advertises the effective size; sender retention, per-source import cache and warm-up follow it. Restart both browser workers and mixer to change it. The active pool never grows or shrinks.

Warm-up registers the complete pool before going on air. The cache must retain at least that pool, with no expiry/eviction churn during the show. This is per source; a buffer from one window is not reusable as another window's allocation.

One copy shortens Chromium ownership

The importer waits for the acquire fence, submits one device copy on a private nonblocking CUDA stream, waits for that copy to finish, then returns the browser frame before publishing downstream. Mixer consumers hold AVP-owned storage, so they cannot pin the Chrome lease through an entire transition. The importer thread can wait on its own stream; “nonblocking stream” does not promise a wait-free CPU path.

Ring size is not compositor latency. A fixed allocation count also does not guarantee no source repeats: an exhausted producer can miss a capture without allocating anything new. Keep both import-churn and on-air delivery counters.

Measured limit

In the matched 30-window/60-fps transition check, six buffers saved about 1 GiB but increased browser repeats from three to 223; neither pool churned. Nine is the current starting point. The 40-window/50-fps result additionally required four workers of ten and the CUDA queue settings. Measured workload and scope.
